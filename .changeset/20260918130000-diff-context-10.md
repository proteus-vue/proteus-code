审批预览的 diff 上下文 3 → 10（并让渲染层的折叠真正生效）

用户拍板：把 `neo-capability::diff::CONTEXT` 从 3 提到 10。

**为什么改**：3 是**未经审视的 unix 默认**（原注释只说"保留的上下文行数"，
没有任何理由）。它对"补丁邮件逐行读"够用，但对**审批预览**不够 ——
用户要据此判断改动对不对，3 行常常交代不清（前面是什么函数、变量从哪来）。
改它有两个独立好处：① 审批时看到更多上下文；② **让折叠未改区块真正生效** ——
折叠阈值是 6，而 3 行上下文永远达不到，于是那个功能实现了却永不触发
（§4.64(az) 记的正是这件事）。

**顺带**：半径变大也会让相距 < 2×半径 的改动**合并进同一个 hunk**，
`@@` 头数量反而变少（可读性提升，不只是变长）。

**新增不变量测试**（这是本轮最重要的产出）：此前 `CONTEXT` 与折叠阈值之间的
耦合**没有任何东西守着** —— 谁把 CONTEXT 调回 ≤6，折叠会再次静默失效，而界面
只表现为"没有折叠把手"，不报错。故加断言：
`fold_threshold_stays_below_the_context_radius`（参数关系）+
`a_real_approval_preview_actually_folds`（用真实生产者端到端验折叠真的发生）。
已验牙齿：把 CONTEXT 改回 3 会立刻红并给出可操作的报错。

**顺带修两处"钉死实现细节"的测试**：`hunk_header_tracks_...` 与 TUI 的跨 crate
往返用例都把"两个改动相距 20 行"写死，半径变 10 后它们被合并成一个 hunk 而失败。
改为**由 CONTEXT 推出距离**（`10 + 2*CONTEXT`），断言"关系"而非"绝对数字" ——
这样以后再调半径不会再打断它们，而它们要守的回归（两侧起始行号必须错开）仍在。

**新增 `--provider edit` 演示桩**：改大文件里的一行，产出**带上下文**的 diff。
其余桩（selftest 整文件重写 / multitool 只有 bash）都产不出这种形状，于是
"审批时能看到多少上下文"此前**没有可离线复现的观察窗口**。

真机验证（按窗口 ID 截图，未抢焦点）：hunk 头为 `@@ -10,21 +10,21 @@`
（半径 10 的确切形状）；25 行 diff 折成 14 行显示，`⋯ 未改 4 行`（13–16）与
`⋯ 未改 7 行`（24–30）与算法逐项对得上；行内强调同时生效。
