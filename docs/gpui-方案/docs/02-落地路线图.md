## Phase -1 · 技术验证（1–2 周，只做一次，目的是避免押错注）

> ## ⚠️ 本轮已实测的四项结论（2026-09-16，macOS 26.5 / rustc 1.95）
>
> **结论：GO —— 但方案 P2/A2/A3 与真实依赖树有矛盾，必须先改（见下）。**
>
> | 验证项 | 结果 | 证据 |
> |---|---|---|
> | 能否编译 | ✅ **能**（`gpui-kit 0.6.1`，151s 增量 / 265s 冷） | `cargo build` exit 0 |
> | 是否需要完整 Xcode | ✅ **不需要**（本机只有 CommandLineTools） | `gpui-pre-macos 0.3.5` **无 build.rs、无 `.metal` 源**，着色器已预编译进库；上游 `gpui 0.2.2` 的 build.rs 才调 `xcrun metal`（那是上一轮终止对比的原因） |
> | CJK 渲染 | ✅ **全绿，且零字体配置** | 真机截图：中/日/韩 + emoji + 中英混排全部正常，无豆腐块（**优于 egui** —— egui 需显式加载 CJK 字体，见 §4.64(e)） |
> | 冷启动到首帧 | ✅ **509–560ms**（< 800ms 预算） | release 构建，3 次取样；首次 1457ms 是冷文件缓存 |
> | release 二进制 | ✅ **8.9MB**（< 30MB 预算） | 未剥离符号 |
>
> **仍未验**：三平台（只测了 macOS）、IME 候选框跟随光标与 preedit 删除后重输、
> 高 DPI 四档。这三项按方案要求必须实测，**不许假设**。
>
> ### 实测推翻/修正了方案里的三处论断
>
> 1. **P2「用 gpui-ce，不要用上游 gpui」与真实依赖树不符。**
>    `gpui-kit 0.6.1`（方案 A1 钦定的组件库）实际依赖
>    **`gpui-pre 0.3.1` + `gpui_platform 0.3.1`**（Longbridge 自己重发布的 Zed 快照，
>    即 `gpui-pre-*` 家族），**不是 `gpui-ce`**。
>    而 `gpui_platform` **在 crates.io 上不存在** —— 只能由 `gpui-kit` 自带的 re-export
>    取用（`gpui_kit::platform`）。若按方案写法手工声明 `gpui-ce` + `gpui_platform`，
>    Cargo 会找不到 crate 或造成两份引擎 —— **恰好是方案 P3 要防的类型身份分裂**。
> 2. **P3「单一 pin」的实现方式要改。** 正确姿势是
>    **普通项目只声明 `gpui-kit` 一个依赖**，其余全部走 `use gpui_kit::*` 与
>    `gpui_kit::{platform, base, component, assets}` 的 re-export。
>    门面层（`<ns>-kit`）应当 re-export **gpui-kit**，而不是自己 pin `gpui-ce`。
>    （实测：只写 `gpui-kit = "0.6.1"` 即可编译并开窗，这正是它 lib.rs 文档的推荐用法。）
> 3. **A2 的论据需复核**：方案说"Longbridge 在 2026-07 把 gpui-component 迁到 gpui-ce"，
>    但 0.6.1 的发布物仍以 `gpui-pre` 为底座。**"用 gpui-ce"这个选型结论与
>    "用 gpui-kit"这个组件选型互相冲突**，二者只能择一为主 —— 实测支持后者
>    （它是唯一能一条依赖就编译开窗的组合）。
>
> ### 对 NEO 的具体含义（方案原文未涉及）
>
> 方案通篇是**绿地项目**（59 处 `<ns>` 占位，未提 NEO）。若要用在 NEO 上：
> - **不能照搬它的 workspace/crate 划分** —— NEO 已有 25 crate 的 L0–L5 分层与
>   架构守卫（`check_architecture.py`）。新宿主应是 **L5 的一个 crate**
>   （与 `neo-host-egui` 并列），不是新的六层体系。
> - 可复用的是它的**纪律**：单一 pin 门面、`verify-layering`（L2/L3 禁 `use gpui::`）、
>   组件 DoD 九宫格、性能预算写进 CI。
> - `neo-text`（Tone/宽度/Markdown/高亮）与 `driver.rs` 的驱动模式**与渲染后端无关**，
>   换 gpui 后仍可复用 —— 这是当初把 `Tone` 抽出共享层的回报。

**目标**：在写下第一行产品代码前，用最小代价确认 GPUI-CE + GPUI Kit 这条路在你的目标平台上真的能跑。

### 任务
- [ ] 建一个临时仓库 `spike-gpui`，**不写任何业务代码**
- [ ] 用 `gpui-ce` + `gpui-component` 跑通 Hello World
- [ ] 三平台各跑一次：macOS / Windows / Linux(Wayland + X11)
- [ ] 验证四个高风险项（见下）

> ```toml

### 四个必须实测的高风险项

## Phase 0 · 工程地基（2–3 周）

**目标**：把「单一 pin」「分层」「CI」这三件事在代码里固化下来。

### 任务
- [ ] 建 workspace，统一 `[workspace.package]` version / edition / lints
- [ ] `rust-toolchain.toml` 锁定 toolchain
- [ ] 建 `crates/<ns>-kit` 门面层（唯一允许依赖 GPUI 的地方）
- [ ] 建 `xtask`，实现三个校验子命令
- [ ] CI：build / test / clippy / fmt / deny / audit
- [ ] 根目录 `NOTICE` + `LICENSES/`（SPDX 归档）

### 必须实现的三个 xtask 校验

```bash
cargo xtask verify-pins      # 除 kit 外无 crate 直接依赖 gpui；Cargo.lock 中 gpui 只有一个版本
cargo xtask verify-layering  # behavior/ 与 ui/ 中不得出现 `use gpui::`
cargo xtask verify-assets    # 图标/字体/主题资源均已生成且无缺失引用
```

`verify-pins` 核心实现参考：
```bash
# 断言无重复 GPUI 实例（有输出即失败）
cargo tree -i gpui-ce --duplicates
```

### DoD
- [ ] `cargo xtask verify-pins && cargo xtask verify-layering` 均退出码 0
- [ ] CI 全绿（三平台 matrix）
- [ ] 空壳应用可启动（一个空白窗口 + 主题切换）

## 10. 给执行 Agent 的十条铁律

1. **绝不**在 `<ns>-kit` 之外声明 `gpui` 依赖。
2. **绝不**在 `<ns>-behavior` / `<ns>-ui` 中出现 `use gpui::`。
3. **绝不**在 `<ns>-ui` 中出现业务名词。
4. **绝不**硬编码颜色，一律 `cx.theme()`。
5. 组件尺寸只用 `xs/sm/md/lg`。
6. 无状态组件一律 `RenderOnce`。
7. 每个组件配 story 条目 + 截图基线。
8. 输入类组件必须有 IME 回归用例，且不可 `#[ignore]`。
9. 升级 GPUI 版本必须走独立 PR + 截图基线比对，禁止夹带功能改动。
10. 拿不准放哪层的代码 → 放 L2（行为层）。表现错误好改，层次错误难救。
