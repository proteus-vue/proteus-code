> 配套文档：00-架构总纲.md

## 1. 先算一笔账：哪些不用你写

GPUI Kit 现成可用（Apache-2.0，Longbridge Pro 生产验证）：

| 类别 | 已存在的组件 |
|---|---|
| 基础 | Accordion, Alert, Attachment, Avatar, Badge, Bubble, Button, Checkbox, Collapsible, DropdownButton, Icon, Image, Kbd, Label, Marker, Message, MessageScroller, Pagination, Progress, Radio, Rating, Skeleton, Slider, Spinner, Stepper, Switch, Tag, TextView, Toggle, Tooltip |
| 表单 | Input, Textarea, **Editor**(Tree-sitter+LSP), Select, Combobox, NumberInput, DatePicker, OtpInput, ColorPicker, Form |
| 布局 | DescriptionList, GroupBox, Root, Theme, Dialog, Notification, Popover, Resizable, Scrollable, Sheet, Sidebar, StatusBar |
| 高级 | Calendar, Carousel, **Command**(命令面板), **Chart**(折线/柱状/面积/饼/蜡烛), List, Menu, Settings, **DataTable**(虚拟滚动/固定列/可调整列宽/排序/单元格选择), **Dock**(可拖拽 Tab/嵌套分栏/边缘停靠/可序列化 Tiles), Tabs, Tree, **VirtualList** |

**结论**：P0 阶段你自研的组件数量应该是 **0 到 5 个**，不是 60 个。

你的真实工作量分布：
- **70%** 业务视图组装（用现成组件拼）
- **20%** 品牌化：Design Tokens、主题、自有组件外观
- **10%** 自研极少数差异化组件

## 2. 渲染缝的务实设计（重要取舍）

### 2.1 不要做「全量抽象」

如果要求每个按钮都走 `RenderBackend` trait，你会**立刻失去 GPUI 的 element diff、脏区剔除、文本整形与字形缓存**，性能倒退，且抽象层本身要维护数万行。**这是烂尾最常见的起点。**

### 2.2 正确做法：缝只开在「自绘表面」

```
常规组件（按钮/输入/表格/菜单…）
    → 直接用 gpui-component，不经过渲染缝
    → 享受 GPUI 全部性能特性

自绘表面（图表 / diff 视图 / 波形 / 拓扑图 / 自定义可视化 / 未来的富文本编辑器）
    → 走 RenderBackend trait
    → 这些地方本来就是你自己写绘制代码，抽象成本≈0
```

这样第一版渲染缝的落地成本只有几百行，但「渲染后端可替换」这件事在架构上**已经被固化**。等你有第二个 backend 时，只需要让更多组件改走缝——渐进式，一次性投入可控。

### 2.3 trait 草案

```rust
// crates/<ns>-render/src/backend.rs

/// 与后端无关的中立场景描述。
/// 设计约束：必须是 Send + 'static，且可廉价克隆（便于 diff）。
#[derive(Default, Clone)]
pub struct Scene {
    pub ops: Vec<Op>,
}

#[derive(Clone)]
pub enum Op {
    FillPath     { path: PathBuf2d, brush: Brush },
    StrokePath   { path: PathBuf2d, brush: Brush, width: f32 },
    FillText     { run: TextRun, origin: Point2d },
    DrawImage    { id: ImageId, dest: Rect2d },
    PushLayer    { bounds: Rect2d, alpha: f32, clip: Option<PathBuf2d>, blur: f32 },
    PopLayer,
}

pub trait RenderBackend: Send + 'static {
    /// 把中立场景提交给具体后端。
    /// GpuiBackend: 翻译成 GPUI element / paint quad
    /// VelloBackend: 翻译成 vello::Scene
    fn render_scene(&mut self, scene: &Scene, surface: &mut Surface);

    /// 文本度量（必须走 HarfRust/Parley 以保证多语言一致）
    fn measure_text(&self, run: &TextRun) -> Size2d;

    fn name(&self) -> &'static str;
}
```

**落地顺序**：先只实现 `GpuiBackend`。**不要提前写 `VelloBackend`**——在只有一个实现时，第二个实现的所有假设都是错的。等 `GpuiBackend` 稳定跑通 3 个月、且你确定要开源引擎了，再动第二个（此时它也是开源的验收标准之一：证明抽象真的成立）。

> 这条是刻意的：只有一个实现的抽象层是**信仰**，两个实现的抽象层才是**设计**。先别把信仰当设计。

## 3. 组件成熟度分级（DoD 九宫格）

任何组件（无论来自 GPUI Kit 还是自研）进入发布前，必须通过下表。
**九项全绿才算 Done，允许「N/A」但必须在 PR 里写明原因。**

| # | 检查项 | 验收方式 |
|---|---|---|
| 1 | **键盘可达** | 纯键盘可完成该组件所有操作；Tab/Shift-Tab 顺序合理 |
| 2 | **焦点可见** | 焦点环在亮/暗主题下均清晰可辨（对比度 ≥ 3:1） |
| 3 | **无障碍** | 有 role + label + state；读屏能读出名称与当前状态 |
| 4 | **IME 安全** | 输入类：中文候选框跟随光标；preedit 删除后重输不崩溃（**必须有回归用例**） |
| 5 | **高 DPI** | 100/125/150/200% 四档无模糊、无 1px 错位 |
| 6 | **双主题** | 亮/暗均通过设计规范；跟随系统切换无闪烁 |
| 7 | **状态完备** | 至少覆盖 default / hover / active / focus / disabled / loading / error |
| 8 | **规模** | 数据型组件：10 万条下滚动帧率 ≥ 60fps（用真实数据量测，不要估） |
| 9 | **视觉回归** | 有截图基线用例，CI 比对像素差异 |

### 3.1 为什么第 4 项要单独强调

IME 是 Rust GUI 生态公认的翻车重灾区。2026 年有人把几十个 Rust GUI 库拿来写同一个 App 实测输入法与读屏，结果是：

- GPUI 无内置 text input（需抄 700-800 行示例）、IME 有越界 panic
- Floem 的 IME 与无障碍是坏的
- Azul 渲染不出系统字体

你用 GPUI Kit 已经绕开了大部分坑（它的 `Editor` 组件支持 20 万行 + LSP），但**必须自己补回归用例**：

```rust
// crates/<ns>-ui/tests/ime_regression.rs

    // 1. 聚焦输入框
    // 2. 合成 IME preedit "中"
    // 3. 删除 preedit
    // 4. 重新输入 "中文"
    // 5. 断言：无 panic，且文本 == "中文"，光标位置正确
}

#[test]
fn ime_candidate_window_follows_cursor() {
    // 断言候选框锚点坐标 == 光标屏幕坐标（含滚动偏移与 DPI 缩放）
}
```

这类测试**必须在 CI 里跑，且不允许 `#[ignore]`**。

## 4. 组件清单与优先级

### P0 — MVP 内部验证（目标：能让人用起来）

全部取自 GPUI Kit，工作量为「集成 + 品牌化」：

- [ ] `Root` + 主题系统（每个窗口第一层必须是 `Root`）
- [ ] `Button` / `Icon` / `Label` / `Tooltip`
- [ ] `Input` / `Textarea`
- [ ] `Sidebar` / `Tabs` / `Dock`
- [ ] `List` / `VirtualList`（变高 item）
- [ ] `Dialog` / `Notification` / `Popover`
- [ ] `Menu` / `Command`（命令面板）
- [ ] `Scrollable`
- [ ] i18n（rust-i18n）+ CJK 字体回退（Fontique）

### P1 — 商业发布门槛（目标：能卖）

- [ ] `DataTable`：虚拟滚动 + 固定列 + 列宽调整 + 排序 + 单元格选择
- [ ] `Editor`：Tree-sitter 高亮 + LSP 诊断/补全/hover
- [ ] `Chart`：至少折线 / 柱状 / 面积
- [ ] `Tree` / `Resizable` / `Sheet` / `StatusBar`
- [ ] `Settings` 界面 + 持久化
- [ ] `Select` / `Combobox` / `DatePicker` / `NumberInput`
- [ ] `Progress` / `Spinner` / `Skeleton` / `Alert`
- [ ] 无障碍：全量组件过 DoD 第 1/2/3 项
- [ ] 每个 P1 组件都有 storybook 条目

### P2 — 差异化（自研，也是未来开源的卖点）

这部分才动 `RenderBackend`：

- [ ] 自绘 `DiffView`（或你的领域专属可视化）
- [ ] 自绘 `Canvas` 通用自绘容器（走渲染缝）
- [ ] 自研的高性能长列表消息流（如 AI 对话：流式追加 + 自动跟随 + 锚点保持）

> AI 客户端类应用的经验：长对话流畅度的第一功臣不是渲染，而是**虚拟滚动**（只挂载可见 turn + 少量 overscan）+ `content-visibility` 式延迟 + 估计高度缓存。Rust 侧同理：VirtualList 只 render 可见区间，滚动锚点在流式内容改变高度时保持。

## 5. 组件契约模板（自研组件必须照此写）

每个自研组件固定三段式：**State（Entity 持有）/ View（RenderOnce 无状态）/ Event**。

```rust
// 1) State：有状态逻辑，放在 Entity 里
pub struct SearchInputState {
    query: String,
    cursor: usize,
    history: VecDeque<String>,
}

impl SearchInputState {
    pub fn new(window: &mut Window, cx: &mut Context<Self>) -> Self { /* ... */ }
}

// 2) Event：对外广播
pub enum SearchEvent {
    Change(String),
    Submit(String),
    Blur,
}

// 3) View：RenderOnce，无状态，只做渲染
pub struct SearchInput {
    state: Entity<SearchInputState>,
    placeholder: SharedString,
    size: Size,           // xs/sm/md/lg
    disabled: bool,
}

impl RenderOnce for SearchInput {
    fn render(self, _: &mut Window, cx: &mut App) -> impl IntoElement { /* ... */ }
}
```

**硬性约束**：
- 无状态组件一律 `RenderOnce`（GPUI Kit 的既有约定，省内存、好组合）
- 有状态逻辑放 `Entity<XxxState>`，通过 `cx.subscribe_in` 收事件
- 尺寸只用 `xs/sm/md/lg` 四档，禁止任意像素值
- 颜色只从 `cx.theme()` 取，禁止硬编码色值
- 每个组件一个 story 条目（既是调试工具也是开源门面）

## 6. 测试金字塔

```
        ╱  E2E（少量）        关键用户旅程：启动→登录→主流程→退出
       ╱────────────
      ╱ 截图基线（CI 比对）   每个 P1 组件 × 亮暗主题 × 2 档 DPI
     ╱────────────────
    ╱ 组件交互测试           键盘事件序列 → 断言状态（含 IME 回归）
   ╱────────────────────
  ╱ 核心逻辑单测（大量）     <ns>-core，无 GUI 依赖，纯函数
 ╱────────────────────────
```

**关键指标**：
- `<ns>-core` 行覆盖率 ≥ 80%（这部分纯逻辑，最容易测，也最该测）
- `<ns>-ui` 每个 P1 组件 ≥ 1 个交互测试 + 1 个截图基线
- E2E 覆盖 3-5 条黄金路径即可，不要铺开（维护成本极高）

## 7. 性能预算（写进 CI，超了就红）

| 指标 | 预算 | 测量方式 |
|---|---|---|
| 冷启动到首帧 | < 800ms | release build，真机 |
| 主线程帧时间 p95 | < 16.6ms | 内置帧时间直方图（GPUI 有 on-screen debug histogram 能力） |
| 10 万行表格滚动 | ≥ 60fps | 真实数据量 |
| 20 万行代码编辑 | 输入延迟 p95 < 50ms | 真实文件 |
| 空闲 CPU | ≈ 0 | 无动画时不应持续出帧（对应 iced reactive rendering 那类优化） |
| release 二进制体积 | < 30MB | 剥离符号后 |

> 「空闲不出帧」这条很多人忽略。它会直接决定用户的笔记本风扇转不转、电池掉多快——而这是应用商店评论区里最常被骂的点之一。

## 8. 发布前最终检查（Release Gate）

负责人逐项签字，任何一项未过不得发版：

- [ ] `cargo xtask verify-pins` 通过（无 GPUI 版本分裂）
- [ ] `cargo xtask verify-layering` 通过（L2/L3 无 `use gpui::`）
- [ ] `cargo deny check licenses` + `cargo audit` 通过
- [ ] NOTICE 文件覆盖全部 Apache-2.0 依赖
- [ ] 全部 P1 组件 DoD 九宫格通过
- [ ] IME 回归用例在**中文、日文、韩文**三种输入法下各跑一遍
- [ ] 读屏实测：VoiceOver / NVDA / Orca 各过一遍主流程
- [ ] 三平台（macOS/Windows/Linux）× 签名 × 公证 × 自动更新链路实测
- [ ] 崩溃上报链路实测：主动 panic 一次，确认 Sentry 收到且符号化成功
- [ ] 性能预算全绿
