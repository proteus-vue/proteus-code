# 架构总纲：Rust + GPUI 桌面应用全链路方案

> 目标：交付一个**可商业发布**的 Rust 原生桌面应用，并为后续**开源渲染引擎 + 组件库**预留干净的切分边界。
> 读者：执行编码的 LLM Agent 与人类架构师。
> 约定：下文 `<ns>` = 你的组织/产品前缀（如 `acme`），全文档统一替换。

---

## 0. 三条不可动摇的前提（先读这个）

### P1. 不要从零写组件库——用 GPUI Kit

已存在且生产验证的事实：

| 项目 | 事实 |
|---|---|
| **GPUI Kit**（Longbridge） | 三层架构：`gpui-base`（无样式行为层）/ `gpui-component`（60+ 带样式组件）/ `gpui-shell`（JS 扩展宿主） |
| 许可证 | **Apache-2.0**，商用无 Qt 式 LGPL 纠结 |
| 生产验证 | **Longbridge Pro** —— 公开上市的商业桌面应用，从第一天起就用它 |
| 能力 | 虚拟表格（20 万+ 行）、虚拟列表（变高 item）、代码编辑器（20 万行 + Tree-sitter + LSP）、Dock 布局（可序列化 Tiles）、Markdown/HTML 渲染、图表、主题系统、i18n、CJK 支持 |
| 活跃度 | 2026-09-09 发布 0.6.1，月下载约 2.7 万，96 位贡献者 |

**结论**：你自己撸组件库 = 重复投入 129K SLoC。正确姿势是「用 GPUI Kit 交付产品，把你真正独有的部分做薄」，同时把可开源的增量反哺回去。

### P2. 用 gpui-ce，不要用上游 Zed 的 gpui

- Zed 官方 2026 年明确表态：聚焦 "business relevant work"，**不为社区做 GPUI 通用化**，并主动把社区指向 `gpui-ce`。
- **GPUI-CE**：社区 fork，独立版本节奏、公开 RFC 治理、只做 UI 框架不夹带编辑器 API，许可 **MIT OR Apache-2.0**（比上游更宽松，可选 MIT）。
- **Longbridge 自己在 2026-07 把 gpui-component 迁移到了 gpui-ce**——生态已经用脚投票。
- 上游 crates.io 的 `gpui` 长期落后于 upstream，形同虚设。

### P3. 单一 Pin 原则是生命线

GPUI 生态的头号杀手是**类型身份分裂**：你的项目和一个插件依赖不同 GPUI commit，Cargo 会编译两份引擎，报出 `expected gpui::WindowContext, found gpui::WindowContext`。

> 硬性规定：**全仓只允许存在一个 GPUI 来源。禁止任何 crate 独立声明 `gpui` 依赖。**
> 由 `<ns>-kit`（门面层）统一 pin 并 re-export，所有下游只允许 `use <ns>_kit::gpui::*`。

## 1. 分层架构

```
┌──────────────────────────────────────────────────────────────┐
│ L4  应用层  <ns>-app                                          │
│      业务视图、命令、状态机、工作流                              │
├──────────────────────────────────────────────────────────────┤
│ L3  设计系统层  <ns>-ui                                       │
│      Design Tokens + 带样式组件（自有品牌外观）                 │
│      ↑ 未来开源目标 B：组件库                                   │
├──────────────────────────────────────────────────────────────┤
│ L2  行为层  <ns>-behavior                                     │
│      无样式、不可见但难做对的东西：焦点陷阱、弹层定位、          │
│      文本编辑引擎、虚拟滚动、无障碍树、IME 交互、快捷键仲裁       │
│      ↑ 未来开源目标 A（与 L1 合为「引擎」）                     │
├──────────────────────────────────────────────────────────────┤
│ L1  渲染抽象层  <ns>-render        ← 「渲染缝」                 │
│      trait RenderBackend { ... }                              │
│      当前实现：GpuiBackend（gpui-ce）                          │
│      未来实现：VelloBackend（vello + wgpu）                     │
│      ↑ 未来开源目标 A：渲染引擎                                 │
├──────────────────────────────────────────────────────────────┤
│ L0  平台层  <ns>-kit（门面）                                   │
│      唯一 pin 点：gpui-ce / gpui-platform / 资源 / 全局 init    │
└──────────────────────────────────────────────────────────────┘
```

### 1.1 为什么必须设「渲染缝」

你的长期目标是**开源渲染引擎**。如果现在把 GPUI 类型直接透进组件签名，两年后你想换 Vello 时，组件库要重写 100%。

所以：**L2 及以上任何代码，禁止出现 `gpui::` 的渲染类型**（`Element`、`PaintQuad`、`Window`、`Context` 等）。渲染相关一律走 L1 的 trait。

这条约束现在看是「过度设计」，它是你未来能不能开源引擎的唯一决定因素。

### 1.2 行为 / 表现分离（采纳 GPUI Kit 已验证的哲学）

> **Behavior belongs to the foundation. Presentation belongs to the application.**

- `gpui-base` 提供 `FocusTrapElement`、`VirtualList`、输入状态机等无样式行为。
- `gpui-component` 在其上套视觉。

你的 L2/L3 严格照此切。判断标准：
- 一段逻辑**去掉颜色尺寸后仍有意义** → L2
- 一段逻辑**本质就是在描述长什么样** → L3

这个切分同时决定了你开源时能否把「引擎」和「皮肤」分开授权。

## 2. 仓库与 crate 划分

### 2.1 单仓多 crate（Cargo workspace）

```
<ns>-desktop/
├── Cargo.toml                 # [workspace] 统一 version / edition / lints
├── rust-toolchain.toml        # 锁定 toolchain，禁止 drift
├── AGENTS.md                  # 给编码 Agent 的硬约束（见 04）
├── crates/
│   ├── <ns>-kit/              # L0 门面：唯一 pin 点
│   ├── <ns>-render/           # L1 渲染抽象 + GpuiBackend
│   ├── <ns>-behavior/         # L2 无样式行为
│   ├── <ns>-ui/               # L3 设计系统 + 带样式组件
│   ├── <ns>-core/             # 与 UI 无关的业务核心（可单测、可 CLI 化）
│   └── <ns>-app/              # L4 组装与入口
├── xtask/                     # 自建任务：pin 校验、资源打包、截图基线
└── docs/
```

**关键**：`<ns>-core` 不依赖任何 GUI crate。它必须能在无显示器环境跑完整测试（`cargo test -p <ns>-core`）。这是 Oxidation 那条「边界清晰的叶子」原则的直接应用——业务逻辑是你最容易保证正确性的部分，别让它被 UI 污染。

### 2.2 门面层的写法（照抄这个模式）

`crates/<ns>-kit/Cargo.toml`：

```toml
[package]
name = "<ns>-kit"
version.workspace = true
edition.workspace = true

[dependencies]
# 唯一允许出现 GPUI 的地方
gpui           = { package = "gpui-ce", version = "<锁定版本>" }
gpui_platform  = { git = "https://github.com/gpui-ce/gpui-ce", rev = "<锁定 commit>" }
gpui-component = { version = "<锁定版本>" }

[features]
default = ["component"]
component = ["gpui-component"]
```

`crates/<ns>-kit/src/lib.rs`：

```rust
// 全仓唯一的 GPUI re-export 出口
pub use gpui;
pub use gpui_platform;
#[cfg(feature = "component")]
pub use gpui_component;

pub fn init(cx: &mut gpui::App) {
    #[cfg(feature = "component")]
    gpui_component::init(cx);
    // 自有全局注册：主题、快捷键表、图标集、i18n
}
```

所有其他 crate 的 `Cargo.toml` 中：

```toml
<ns>-kit = { path = "../<ns>-kit" }
# 绝不允许出现 gpui = ...
```

### 2.3 Pin 校验任务（必须实现）

`xtask` 提供 `cargo xtask verify-pins`，失败即 CI 红：

```
检查项：
1. 遍历所有 Cargo.toml，断言除 <ns>-kit 外无 crate 直接依赖 gpui / gpui_platform / gpui-component
2. 解析 Cargo.lock，断言 gpui / gpui-ce 只出现一个版本
3. 断言 rust-toolchain.toml 与 CI 使用同一 toolchain
```

第 2 条可以直接用：`cargo tree -i gpui-ce --duplicates`（出现重复即失败）。

## 3. 许可证与合规

| 组件 | 许可证 | 商用影响 |
|---|---|---|
| gpui-ce | MIT OR Apache-2.0 | ✅ 可选 MIT，最宽松 |
| gpui-component / GPUI Kit | Apache-2.0 | ✅ 需保留 NOTICE |
| Lucide 图标 | ISC | ✅ 需 attribution |
| 你的渲染引擎 / 组件库 | **建议 Apache-2.0** | 见下 |

**执行项**：
- [ ] 仓库根目录建 `NOTICE`，逐条列出 Apache-2.0 依赖的版权声明（这是 Apache-2.0 的硬性要求，不是可选项）
- [ ] 建立 `LICENSES/` 目录，用 SPDX 标识符归档每个依赖的许可文本
- [ ] CI 加 `cargo deny check licenses` 或 `cargo-about`，把许可合规变成机器检查
- [ ] 你的开源产物选 **Apache-2.0 而非 GPL**：GPL 会把 Slint 式的双授权困境原样复制一遍，吓跑商业用户

**关于「后面开源」的授权策略**：
- 渲染引擎 + 行为层 → Apache-2.0，允许所有人白嫖（这是拿 adoption 的代价）
- 设计系统层（L3）→ 可考虑保留自有品牌外观，或双授权
- 应用层（L4）→ 闭源

## 4. 商业可用性基线（缺一不可）

这部分是「能跑」和「能卖」的分界线。逐项打勾，缺任一项都定义为**不可发布**。

### 4.1 输入与国际化
- [ ] **CJK 输入法**：中文/日文候选框跟随光标定位、preedit 高亮、输入法切换不丢字符
- [ ] IME 崩溃防护：删除 preedit 后重输不 panic（GPUI 曾有越界 panic 前例，必须有回归用例）
- [ ] 文本基线：HarfRust 整形，阿拉伯语/希伯来语 RTL、天城文组合字符、emoji ZWJ 序列

### 4.2 无障碍（很多企业客户的硬性采购门槛）
- [ ] 每个交互元素暴露无障碍 ID 与角色
- [ ] 键盘全可达：Tab 序、焦点环可见、Esc 关闭弹层、焦点陷阱
- [ ] 读屏可朗读（macOS AX / Windows UIA / Linux AT-SPI）
- [ ] 高对比度模式

### 4.3 显示
- [ ] 高 DPI：100% / 125% / 150% / 200% 无模糊、无错位
- [ ] 多显示器跨屏拖拽时缩放因子切换正确
- [ ] 亮/暗主题跟随系统 + 手动覆盖

### 4.4 稳定性
- [ ] 崩溃上报：Sentry Rust SDK（`features = ["backtrace","contexts","panic"]`）+ minidump 捕获原生崩溃
- [ ] 自定义 panic hook：崩溃前 flush 日志与遥测
- [ ] 全局错误边界：单个视图渲染失败不白屏，降级为错误占位 + 上报
- [ ] 日志落盘到用户目录，保留 7 天，用户可一键导出

### 4.5 分发与更新
- [ ] macOS：Developer ID 签名 → `notarytool` 公证 → `stapler` 钉票 → 产出 `.dmg`
- [ ] Windows：Authenticode 签名（EV 证书或 Azure Trusted Signing）→ `.msi` / NSIS
- [ ] Linux：`.deb` / `.rpm` / `.AppImage`
- [ ] 自动更新：签名更新包 + CDN 分发 + 灰度通道（stable / beta）
- [ ] 包管理器：Homebrew tap、winget、Scoop bucket（CI 自动提 PR 更新 SHA256）

### 4.6 安全与合规
- [ ] 本地数据加密（密钥存系统钥匙串，不落明文）
- [ ] 依赖审计：CI 跑 `cargo audit` + `cargo deny`
- [ ] SBOM：CycloneDX 格式随发布产物生成
- [ ] 遥测默认关闭，首次启动明确询问，可随时关闭

> **建议**：4.4 / 4.5 用 `cargo-dist` 串 CI，它原生支持签名、公证、SBOM、GitHub Releases 与安装器生成。不要自己写这套脚本。

## 5. 开源切分边界（提前设计，事后切不动）

未来要开源时，希望是「复制两个目录出去就能建新仓」。所以现在就约束依赖方向：

```
依赖方向只能向下，严禁反向或跨层：

<ns>-app      → ui, core, kit
<ns>-core     → (无 GUI 依赖)
<ns>-ui       → behavior, render, kit
<ns>-behavior → render, kit
<ns>-render   → kit
<ns>-kit      → gpui-ce, gpui-component
```

**开源时的动作**：

| 开源产物 | 包含 crate | 前置条件 |
|---|---|---|
| **渲染引擎** | `<ns>-render` | 至少要有第二个 backend 实现（哪怕只到 prototype），否则「引擎」名不副实 |
| **行为/组件库** | `<ns>-behavior` + `<ns>-ui` | 全仓无 `<ns>-` 业务类型泄露；有独立 storybook / 示例 gallery |

**现在就要做的事**（成本近乎为零，事后改成本极高）：
1. `<ns>-ui` 中**禁止出现任何业务名词**（客户名、订单、工作流…）。组件只认识 `Item`、`Row`、`Entry`。
2. `<ns>-behavior` 与 `<ns>-ui` 的文档注释、错误信息、示例全部写成「独立产品」口吻，不引用应用上下文。
3. 每个 crate 自带 `README.md`、`LICENSE`、`CHANGELOG.md`，即使暂时不开源。
4. `<ns>-ui` 提供 `story` feature 与示例 gallery——这既是开发调试工具，也是未来开源的第一印象。

## 6. 风险登记册

| 风险 | 影响 | 缓解 |
|---|---|---|
| GPUI-CE 治理未定型、可能再分裂 | 高 | 门面层吸收变化；同时给 `gpui-unofficial` 留一条 `[patch]` 逃生通道 |
| gpui-component 与 gpui-ce 版本错配 | 高 | 单一 pin；`xtask verify-pins` 进 CI；升级走独立 PR + 截图基线比对 |
| 上游 Zed 架构变更导致 gpui-ce 难跟进 | 中 | 渲染缝降低耦合；L2 行为层自有实现占比逐月提升 |
| IME / 无障碍细节缺陷（招致差评的主要来源） | 高 | 见 01 号文档「组件 DoD」，逐组件验收，不允许「整体差不多」 |
| 单人/小团队维护 129K SLoC 依赖 | 中 | 优先用 GPUI Kit 现成组件；自研部分控制在 L1/L2 |
| 渲染缝被绕过（开发者图省事直接 use gpui） | 高 | CI lint 拦截：L2/L3 中 `use gpui::` 直接编译失败 |

**渲染缝的 CI 强制**（`clippy.toml` + 自定义 lint 或简单 grep 脚本）：

```bash
# xtask verify-layering
! grep -rn "use gpui::" crates/<ns>-behavior/src crates/<ns>-ui/src
# 命中即失败
```

## 7. 决策摘要（ADR 速览）

| # | 决策 | 理由 |
|---|---|---|
| A1 | 采用 GPUI Kit 而非自研组件库 | 60+ 组件、Apache-2.0、Longbridge Pro 生产验证 |
| A2 | 采用 gpui-ce 而非上游 gpui | Zed 已停止社区通用化；gpui-ce 社区治理、MIT OR Apache-2.0；Longbridge 已迁移 |
| A3 | 单一 pin 门面层 | 杜绝 GPUI 类型身份分裂 |
| A4 | 设 L1 渲染缝 | 未来开源渲染引擎的唯一可行性来源 |
| A5 | 行为/表现分层 | 已验证的架构哲学；开源时可分开授权 |
| A6 | core 无 GUI 依赖 | 可测试性； Oxidation「摘叶子」原则 |
| A7 | 开源产物用 Apache-2.0 | 避免复制 Slint 的双授权困境 |
| A8 | 分发用 cargo-dist | 签名/公证/SBOM 已被解决，不要自研 |
