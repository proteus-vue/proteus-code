# NEO 内核分层与依赖方向

## 六层架构

```
┌──────────────────────────────────────────────────────────┐
│ L5  HOST        宿主层（不含业务逻辑，只消费事件流）        │
│     dsh-host-tui (ratatui)  dsh-host-web (axum+WS)        │
│     dsh-exec (无头/CI)      dsh-cli (multitool 入口)       │
├──────────────────────────────────────────────────────────┤
│ L4  ORCHESTRATION  目标编排层                              │
│     dsh-orchestration                                     │
│     Goal 引擎：Plan → Code → Review → Learn                │
│     Checkpoint / 断点恢复 / 子任务调度                      │
├──────────────────────────────────────────────────────────┤
│ L3  CAPABILITY   能力层（4 类扩展点中的 3 类在此）          │
│     dsh-capability                                        │
│     Tool(Shell-First + apply_patch) / Skill / Subagent     │
│     MCP client                                            │
├──────────────────────────────────────────────────────────┤
│ L2  CORE        内核（★ 不可替换，这是与 DSH 的根本分歧）   │
│     dsh-core                                              │
│     Session 状态机 / run_turn 主循环 / ContextManager      │
│     ToolRouter / ApprovalGate / ModelProvider(扩展点)      │
├──────────────────────────────────────────────────────────┤
│ L1  PLATFORM    平台层（OS 原语）                          │
│     dsh-sandbox   Seatbelt / Landlock+bwrap+seccomp / ACL │
│     dsh-platform  process hardening / fs notify / git     │
├──────────────────────────────────────────────────────────┤
│ L0  PROTOCOL  ★ 线协议（纯数据，无业务，依赖图真正的底部）   │
│     dsh-protocol    Op / EventMsg / SandboxMode / Item    │
└──────────────────────────────────────────────────────────┘

旁挂（不参与层次，任何层可用）：
     dsh-session   JSONL append-only 会话真相源
     dsh-config    四级配置 + AGENTS.md 级联
```

## 依赖方向铁律

> **依赖只能向下，不能向上，不能跨层向上回指。**

```
L5 → L4 → L3 → L2 → L1 → L0
```

> **为什么 L0 是协议而不是平台？**
> 因为 `dsh-sandbox` 需要复用协议里的 `SandboxMode` 等共享枚举，而 `dsh-protocol` 零业务依赖。
> **编号必须反映真实依赖深度** —— 协议才是依赖图的底，平台在它之上。
> 这一点不是纸上推演，是架构守卫实际跑出来后修正的（最初把平台编为 L0，被判"向上依赖"）。

**具体禁令**（由 `05-验证/checks/check_architecture.py` 强制执行）：

| 层 | 允许依赖 | 禁止依赖 |
|---|---|---|
| L5 host | L4, L3, L2, L1, L0 | 不得依赖其他 host crate |
| L4 orchestration | L3, L2, L1, L0 | **L5** |
| L3 capability | L2, L1, L0 | **L5, L4** |
| L2 core | L1, L0 | **L5, L4, L3** |
| L1 platform/sandbox | L0 | **L2 及以上** |
| L0 protocol | 无（仅 serde） | **任何 crate** |

**为什么 L2 绝不能依赖 L3**（这是最容易犯的错）：
L2 的 ToolRouter 只认 `Tool` trait（定义在 L2 或 L1），**不认具体工具实现**。
具体工具由 L3 注册进来（依赖注入），这样内核才能在不引入任何具体工具的情况下编译和测试。

## 与 DSH 的根本分歧

| | DSH | NEO |
|---|---|---|
| agent loop | 可替换插件 | **固定在 L2** |
| UI | 可替换插件 | **L5 宿主，只消费事件** |
| 存储 | 可替换插件 | **`dsh-session` 固定实现**（格式可版本化，实现不替换） |
| 扩展方式 | 任意层插拔 | **仅 4 类扩展点**：Tool / Skill / Subagent / ModelProvider |

## 为什么固定内核不损失扩展性

几乎所有真实需求都落在这 4 类扩展点里：
- 要新能力 → 写 Tool 或接 MCP
- 要复用工作流 → 写 Skill
- 要并行分工 → 写 Subagent（Markdown 定义，对齐 ZCode）
- 要换模型 → 实现 ModelProvider trait

**换 loop / 换存储 / 换 UI 的需求，在实践中极少，但代价极高。**
