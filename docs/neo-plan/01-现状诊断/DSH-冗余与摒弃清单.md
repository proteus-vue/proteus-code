# DSH 现状诊断：冗余与摒弃清单

> 诊断对象：`deepseek-ai/deepseek-harness` v0.1.0-rc.6（2026-08-13 开发者预览版）
> 事实基线：MIT / TypeScript / Cordis 插件内核 / pnpm workspace / 219 个 workspace 包 / 约 453K 行 TS / 100+ 官方插件 / Node 22.19+ / 默认 3080 端口。

---

## 0. 先说 DSH 做对了什么（这些要保留）

| 优点 | 处置 |
|---|---|
| **append-only 会话日志，每次喂给模型的都留痕** | ✅ 全量保留，升级为内核一等公民 |
| **fail-closed 沙箱阶梯**（read-only / workspace-write / danger-full-access；无可用后端直接拒绝） | ✅ 保留，下沉到 L1 平台层 |
| **无 API Key 的测试回放**（JSONL 既作输入又作期望输出，diff 即断言） | ✅ 保留并强化为 NEO 的核心验证手段 |
| **模型适配器可插拔**（DeepSeek / OpenAI / Claude / Bedrock 等） | ✅ 保留为 4 类扩展点之一 |
| **沙箱三平台原生实现**（bubblewrap/Landlock、seatbelt、write-restricted token） | ✅ 保留，Rust 重写更好做 |

## 1. 冗余过重设计（逐条摒弃）

### R1 —— "一切皆插件"导致的过度抽象 【最高优先级摒弃】

**现状**：模型适配器、工具注册表、会话日志、沙箱、存储、**agent loop 本身**、调度器、**UI** 全部可替换插件。

**问题**：
- 一次工具调用的调用栈要穿过 N 层插件解析与服务查找，**stack 极深**
- 出错时 `info` 只告诉你"插件 X 的第 N 步"，不知道真实业务位置
- 插件间通过事件/服务隐式通信，**依赖关系不可静态分析**
- 直接放大了本项目此前已确认的痛点："AI 改完 → 等重启 → 报错信息不完整 → AI 只能猜"

**结论**：这是 AI 辅助开发时代的**负资产**。框架灵活性换来的复杂度，收益远不抵成本。

**替换**：固定六层内核（L0–L5），只开放 **4 类扩展点**：Tool / Skill / Subagent / ModelProvider。
内核职责（agent loop、状态机、上下文、沙箱判定）**不可替换**，只能通过配置调参。

---

### R2 —— 219 个 workspace 包，粒度失控

**问题**：改动一处常跨多个包；`pnpm build` 全量成本高；新人认知负担极大；AI 读代码时上下文被包名噪音占满。

**替换**：12 个 crate（见 `06-原型代码/`），按层划分，依赖严格单向。

---

### R3 —— 100+ 官方插件默认全量

**问题**：冷启动与配置面巨大；大量用不到的能力进入工具描述，占用模型上下文、干扰工具选择。

**替换**：**按需注册**。默认只注册 Shell-First 工具集（bash + apply_patch + 少量内置）；Skill / MCP / Subagent 显式声明才加载。
对齐 Codex 的 **Shell-First** 哲学：一个 bash 执行器替代数百专用工具。

---

### R4 —— 4 种预制运行模式（Standard / PTC / Minimal / Creator）边界模糊

**问题**：模式本质是"插件集"的笛卡尔组合；Standard 与 PTC 能力高度重叠（PTC 只是把工具调用换成生成 TS 脚本）；Creator 是开发态模式，混在运行时模式里不伦不类。

**替换**：**正交双轴**。
- 轴一（能力/自主度）：5 档执行模式（吸收 ZCode）
- 轴二（安全边界）：3 档沙箱（保留 DSH/Codex 既有设计）
- 取消"模式=插件集"的耦合，改为两个独立旋钮的显式组合
- PTC 的"用程序编排多步操作"价值，改由 **Subagent + 工作流 Skill** 承接，不单独设模式

---

### R5 —— vendor Cordis 9 个包 + 18 条本地修改

**问题**：与上游 Cordis 脱钩，上游演进无法合入；18 条本地 patch 是长期维护债；且 Cordis 的"时空可组合性"范式与 NEO 的"固定内核"立场直接冲突。

**替换**：**不引入任何插件框架**。内核用普通 Rust trait + 显式注册即可。
（若确需插件元框架，也应该是 NEO 自研的 30 行 registry，而非 vendored 通用框架。）

---

### R6 —— 社区 Electron 桌面壳

**问题**：安装包 78MB+；进程管理 / 端口分配 / 系统托盘 / 日志落盘全是胶水；且 DSH 本身是 Node 程序，**Node 依赖无论如何省不掉**——Electron 只多带了一份 Chromium。

**替换**：Web 宿主（Axum + WebSocket/SSE）+ TUI 宿主（ratatui）。
桌面形态若必须要，后续用极薄壳或直接浏览器访问，**不为此保留 Electron**。

---

### R7 —— PTC 模式额外叠加 TS 脚本运行时

**问题**：在沙箱之上再叠一层 TS 执行环境，带来独立的依赖解析、错误映射、资源限制问题；与"摒弃过度抽象"的立场矛盾。

**替换**：不设独立运行时。需要多步编排时，由 **Subagent 工作流** 或 **模型直接生成 shell 脚本**（走沙箱）完成。

---

## 2. 上游不稳定风险（必须前置处理）

DSH README 明确声明 **"THERE WILL BE COMPATIBILITY-BREAKING CHANGES"**。

**处置策略**（详见 `07-迁移/上游同步策略.md`）：
1. NEO 是**重写**而非 fork，**不承诺与上游 DSH 双向同步**
2. 从上游只**单向借鉴**：会话日志格式、沙箱阶梯设计、测试回放思路
3. 上游 DSH 继续演进时，NEO 只吸收"设计思想"，不合代码
4. 二开期间保留一份 DSH `0.1.0-rc.6` 冻结快照作为行为对照基线
