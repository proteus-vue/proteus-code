# 上游 DSH 同步策略

## 前提事实
DSH README 明示：**"THERE WILL BE COMPATIBILITY-BREAKING CHANGES"**。
版本 0.1.0-rc.6，2026-08-13 发布，两天 star 破 10 万，迭代极快。

## 结论：不双向同步，只单向借鉴

| 做法 | 决策 |
|---|---|
| fork DSH 并持续 rebase 上游 | ❌ **不做**。NEO 是 Rust 重写，与 TS 上游无共同代码基线 |
| 上游出新版本就合并代码 | ❌ **不做** |
| 从上游**借鉴设计思想** | ✅ 做 |
| 上游的会话格式/沙箱阶梯/回放测试思路 | ✅ 吸收 |
| 冻结一份 `0.1.0-rc.6` 快照作行为基线 | ✅ 做 |

## 为什么这是对的

1. **语言不同**：TS → Rust，没有可合并的代码单元
2. **架构立场相反**：上游是"一切皆插件"，NEO 是"固定内核"（ADR-0001）。合上游 = 自我否定
3. **上游不稳定**：preview 阶段每周破坏性变更，跟随成本高于收益
4. **DSH 的核心价值已经拿走**：append-only 会话、fail-closed 沙箱、无 Key 回放测试 —— 这三样是设计思想，不需要跟代码

## 定期审视（建议每季度）

检查 DSH 上游是否有：
- 新的沙箱后端或安全机制 → 评估吸收到 L1
- 会话格式改进 → 评估 NEO JSONL schema 版本升级
- 被验证有效的交互范式 → 评估吸收到 L5

**审视 ≠ 合并。** 只搬思想，不搬代码。
