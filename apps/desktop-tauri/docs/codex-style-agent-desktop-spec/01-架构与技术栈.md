# 01 架构与技术栈

## 1.1 目标形态（一句话）

Electron 桌面壳 + React 前端 + 独立 Agent 引擎；本地优先，代码不出机器。

## 1.2 进程模型

三家实测都是 **Electron + 三段式（main / preload / renderer）** `[C][M][Z]`。

```
┌─────────────────────────────────────────────────────────┐
│ Main Process                                            │
│  窗口管理 / 原生能力 / IPC 路由 / 自动更新               │
│  ├─ node-pty        终端                                │
│  ├─ file watcher    文件监听（MiMo 用 @parcel/watcher） │
│  └─ Agent 引擎宿主  ★ 见 1.3                            │
├─────────────────────────────────────────────────────────┤
│ Preload: contextBridge，只暴露白名单 API                │
├─────────────────────────────────────────────────────────┤
│ Renderer: React 19 + Vite + Tailwind v4 + shadcn/ui     │
└─────────────────────────────────────────────────────────┘
```

**选型建议**：Electron。理由——三方无一例外都选了它，生态（pty、watcher、原生模块、自动更新）最完整。Tauri 在 pty 和 Node 原生模块上坑更多，除非你明确要小体积。

实测规模参考：

| 项 | Codex `[C]` | MiMo `[M]` |
| --- | --- | --- |
| 主 UI 包 | `app.asar` 296MB（含多语言与语言包） | `app.asar` 常规量级 |
| Agent 引擎 | `codex` 220MB + `codex-code-mode-host` 62MB（Rust） | `out/main/node.mjs` 36MB（Bun 打包的 TS） |
| IPC 通道 | — | 312 条 |
| 快捷键 | — | 35 个 |

## 1.3 Agent 引擎：放主进程还是子进程

**这是第一个要定的决策**，它决定后面所有配置注入方式。

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A. 主进程内 import** | `await import("./engine-entry.mjs")` | 直接共享 `process.env`，配置注入最简单；无跨进程序列化 | 引擎卡死会拖死 UI |
| **B. 独立子进程** | `spawn()` 带完整 `env` | UI 永不被阻塞；崩溃可重启 | IPC 协议要自己定；env 需显式透传 |

**实测**：MiMo 选了 A（主进程内 `await import("./engine-entry.mjs")`）`[M]`；Codex 选了 Rust 独立二进制 `[C]`。

**推荐**：
- 起步用 **A**（省事，配置/调试都简单），但引擎必须做成**可中断的异步循环**，每轮 yield 回事件循环。
- 一旦要做长时间无人值守任务（后台自动化），迁到 **B**。
- 无论哪种，**env 透传必须是 `{...process.env}` 全量**，不要用白名单构造——白名单会让所有外部注入的环境变量失效（MiMo 的教训）。

## 1.4 前端技术栈

| 层 | 选型 | 依据 |
| --- | --- | --- |
| 框架 | React 19 | 三家一致 `[C][M][Z]` |
| 构建 | Vite（electron-vite 分三端） | `[M]` |
| 样式 | **Tailwind v4** | 三家一致 `[C][M][Z]`，这是配色天然接近的根因 |
| 组件 | shadcn/ui（Radix 底座） | MiMo 18/26、ZCode 14/26 语义令牌命中 `[M][Z]` |
| 代码高亮 | Shiki | 三家一致 `[C][M][Z]` |
| 终端 | xterm.js | `[M]`（173 处）、`[Z]` |
| Markdown | react-markdown + remark-gfm + KaTeX | `[M][Z]` |
| 图表/图 | Mermaid | `[M][Z]` |
| 分栏 | react-resizable-panels | 三家一致 `[C][M][Z]` |
| 状态 | Zustand 或 Redux Toolkit | `[Z]` 用 Redux |
| 命令面板 | cmdk | `[C][Z]` |

**Markdown 渲染安全**：必须走 `rehype-sanitize` / `rehype-harden`（ZCode 两者都装了 `[Z]`）。模型输出会进 DOM，不做净化等于 XSS。

## 1.5 IPC 设计

MiMo 有 312 条 IPC 通道 `[M]`。别手写 312 个 handler，用**类型化的 RPC 层**：

- 主进程暴露一组命名空间化的方法（`session.*` / `fs.*` / `git.*` / `config.*`）
- preload 用 `contextBridge` 只挂这一层，renderer 永远拿不到 `ipcRenderer` 本体
- 所有跨进程调用带超时与取消（Agent 任务尤其重要）

## 1.7 依赖规模参考

ZCode 前端 `node_modules` 顶层 460 个包 `[Z]`，包含：`@radix-ui`、`@streamdown`、`@shikijs`、`@xterm`、`@tanstack`、`@dnd-kit`、`@xyflow`、`rrweb`、`mermaid`、`echarts`、`pdfjs-dist`、`playwright-core`、`ssh2`、`@modelcontextprotocol`、`@opentelemetry`、`lucide-react`、`framer-motion`。

MiMo 因为是 Bun 打包，运行时依赖很少，只在 `package.json` 声明了 7 个 `[M]`。

**建议**：照 ZCode 那个量级准备，但**按需引入**——`rrweb`、`echarts`、`ssh2`、`playwright-core` 这些都是特定功能才需要，不要开局全装。
